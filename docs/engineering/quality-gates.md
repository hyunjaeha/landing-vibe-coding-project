# 품질 게이트

이 문서는 배포 전 반드시 확인할 품질 기준을 정의합니다. 요구사항 원문은 `docs/product/mvp-scope.md`, 디자인 기준은 `docs/design/landing-page-brief.md`, 아키텍처 기준은 `docs/engineering/architecture.md`를 기준으로 합니다.

## 문서 역할

- 이 문서는 구현 완료 여부를 판단하는 검증 기준만 다룹니다.
- 기능 요구사항, 디자인 토큰, 운영 절차를 반복해서 설명하지 않습니다.
- 테스트나 점검 중 기준이 불명확하면 먼저 원천 문서를 확인합니다.

## 접근성 점검

- 본문 텍스트와 배경 대비는 WCAG AA 기준인 4.5:1 이상을 목표로 합니다.
- 버튼 텍스트는 배경과 충분한 대비를 가져야 합니다.
- 마감, 오류, 성공 상태는 색상만으로 전달하지 않고 텍스트를 함께 표시합니다.
- 키보드 포커스 상태는 시각적으로 확인할 수 있어야 합니다.
- 폼 라벨은 입력 필드와 명확히 연결되어야 합니다.
- 오류 문구는 해당 필드 바로 아래 또는 가까운 위치에 표시합니다.

## 개인정보 점검

- 문의 폼은 MVP에 필요한 최소 개인정보만 요구합니다.
- 이름, 전화번호, 희망 일정 외 불필요한 개인정보를 요구하지 않습니다.
- 문의 내용 입력 근처에 민감정보 입력 금지 안내를 표시합니다.
- 개인정보 수집 동의가 없으면 제출되지 않아야 합니다.
- Supabase 서비스 역할 키와 관리자 비밀 값은 브라우저 코드에 포함되지 않아야 합니다.
- 운영자가 삭제 요청을 받았을 때 처리할 기준은 `docs/operations/operating-guide.md`와 충돌하지 않아야 합니다.

## 반응형 점검

| 화면 | 확인 기준 |
| --- | --- |
| 모바일 360px 이상 | 핵심 정보, 일정 카드, 문의 폼이 한 열로 표시되고 가로 스크롤이 없습니다. |
| 큰 모바일 430px 이상 | 핵심 정보가 과밀하지 않고 폼은 한 열을 유지합니다. |
| 태블릿 768px 이상 | 일정과 안내 영역이 읽기 좋은 폭을 유지합니다. |
| 데스크톱 1024px 이상 | 본문 최대 폭이 과하게 넓지 않고 첫 화면 이후 섹션 일부가 자연스럽게 이어집니다. |

## 데이터 점검

- Supabase 문의 테이블에 문의가 저장됩니다.
- 저장된 문의에는 접수 시간이 포함됩니다.
- 문의 내용이 비어 있어도 필수값이 있으면 저장할 수 있습니다.
- 제출 실패 시 빈 성공 메시지를 표시하지 않습니다.
- 관리자 목록 로딩 실패 시 실패 안내를 표시합니다.

## 배포 전 최소 시나리오

1. 모바일 너비에서 랜딩 페이지를 엽니다.
2. 워크숍명, 대상자, 일정, 장소, 가격을 확인합니다.
3. 문의 폼에 이름, 전화번호, 희망 일정을 입력합니다.
4. 개인정보 수집 동의에 체크하고 제출합니다.
5. 접수 완료 메시지를 확인합니다.
6. Supabase 문의 테이블에 데이터가 저장됐는지 확인합니다.
7. 관리자 접근 보호 없이 문의 목록에 접근할 수 없는지 확인합니다.
8. 접근 보호를 통과한 뒤 문의 목록에 새 문의가 보이는지 확인합니다.
9. 운영 체크리스트가 정적으로 표시되는지 확인합니다.
10. 실제 배포 URL에서 새로고침 후 다시 접근되는지 확인합니다.

## 실패 시 처리 기준

- 게이트 실패가 제품 범위 문제라면 `docs/product/mvp-scope.md`를 먼저 확인합니다.
- 화면 상태 문제라면 `docs/product/user-flow.md`와 `docs/design/landing-page-brief.md`를 확인합니다.
- Supabase, 관리자 보호, 환경변수 문제라면 `docs/engineering/architecture.md`를 확인합니다.
- 운영 처리 문제라면 `docs/operations/operating-guide.md`를 확인합니다.
